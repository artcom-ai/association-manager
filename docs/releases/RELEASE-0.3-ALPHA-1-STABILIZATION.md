## 3. ELESYTH continuous seeding - root cause and fix

Root cause: see Section 1's core-bug finding. `admin_init`-hooked, always-overwrite seeders is what made "idempotent" mean "keeps clobbering admin edits" instead of "runs once."

Fix (reuses Core's existing `MigrationInterface`/`MigrationLoader`/`MigrationRunner` - no new migration mechanism, per this task's explicit constraint):

- `MigrationRunner`'s tracking-option key became an optional constructor parameter, defaulting to its previous hardcoded value (`association_manager_migrations`) - fully backward compatible, generic infrastructure, not ELESYTH-specific.
- New `ImplementationMigrator::installPending()` in ELESYTH: `MigrationLoader` loads `migrations/` (new directory, sibling to `src/`), run through `new MigrationRunner('ame_migrations')` - a tracking option isolated from Core's own.
- Four new migration files (`migrations/001_seed_certificate_templates.php` ... `004_seed_memberpress_field_mappings.php`), each a thin wrapper around the existing, unmodified seeder classes.
- `Plugin::seedContent()` replaced by `Plugin::runPendingMigrations()`, still hooked on `admin_init` (self-healing for code-only updates to an already-active install, mirroring `Kernel::registerHooks()`) and now also called from a new `register_activation_hook`.
- A migration only ever executes once per id, tracked permanently. Future implementation migrations are supported by simply adding a new numbered file.

**Correction from a first independent review (fixed before any of it was committed)**: the fix as first implemented only solved the problem going forward from a genuinely fresh `ame_migrations` state - it did not account for a site that had already been running the *old*, pre-migration `admin_init`-reseed-forever code, and so already had template rows in its database the moment it upgraded to this fix. On such a site, migrations `001`/`002` would still see "not yet recorded as executed" (correctly, since `ame_migrations` is new) and run once - but `CertificateTemplateSeeder`/`NotificationTemplateSeeder` themselves were still unconditional upserts, so that one run would silently overwrite whatever was currently stored, admin-edited or not. Fixed by making both seeders create-if-missing, checked via the repository's existing `find()` method.

**Correction from a second independent review (also fixed before any of it was committed) - the "create-if-missing" fix above was itself broken**: it assumed the first time these seeders ever run, the repository is empty. It never is. **Core's own migrations (`009_create_notification_templates_table.php`, `012_create_certificate_templates_table.php`) already insert English default rows before ELESYTH can ever activate at all** - Core must already be active for ELESYTH to run, and Core's migrations run at Core's own activation. So `find() !== null` was true on every site, fresh or legacy, and the create-if-missing seeders never actually seeded Greek content anywhere - the original bug (templates staying in English / an edit getting reverted) was never actually fixed by the first correction, only its most visible symptom was.

The actual fix required distinguishing "this row is still Core's untouched English default" from "an administrator (or ELESYTH itself, earlier) already wrote something deliberate here" - and the second review was explicit that this must not be inferred by comparing the row's *text* (Core's default copy can change across releases, and there's no way to verify a text-based guess against real persisted state either way). The mechanism actually used: a real `is_default` column added directly to migrations 009/012's own `CREATE TABLE` statements (safe specifically because this plugin has never shipped a release - no site anywhere is running an older version of those migrations for the edit to fail to reach), set to `1` only by those migrations' own direct inserts. `CertificateTemplateRepository`/`NotificationTemplateRepository::save()` always persist `0`, regardless of caller - any deliberate write, admin or seeder, permanently ends a row's "still the untouched default" status. ELESYTH's seeders now check this flag (`CertificateTemplate`/`NotificationTemplate::$isDefault`), not mere existence.

A related, previously out-of-scope gap was closed in the same pass: `FieldDefinitionRepository::save()` (migration 003) and `FieldMappingRepository::save()` (migration 004) had the identical ignored-`$wpdb`-return-value bug the certificate/notification repositories had before the first correction - both now throw `DatabaseWriteException` too. All four of ELESYTH's implementation migrations were re-audited end-to-end for this class of bug; each migration's `up()` only calls `find()`/`save()` on its one repository interface, so this is now a complete accounting.

**Correction from a third independent review (also fixed before any of it was committed) - the second correction's schema rollout was not itself upgrade-safe**: the second correction's ADR text claimed editing migrations 009/012 in place was safe "because this plugin has never shipped a release." That reasoning was wrong and has been removed: "never shipped a public release" is not the same as "no database anywhere has ever run these migrations" - any development, staging, or the ELESYTH pilot's own environment that had already activated Core before the second correction landed already has 009/012 recorded as executed, under the *original* schema (no `is_default` column) - `MigrationRunner` never re-runs a completed migration id, so editing those files retroactively has no effect on such a database, yet the revised repositories unconditionally reference `is_default` in every query. This would fail with a real "Unknown column" MySQL error the moment either repository is used against such a database.

**The fix**: two new, purely additive Core migrations - `025_add_is_default_to_notification_templates_table.php` and `026_add_is_default_to_certificate_templates_table.php` - using the same "repeat the full desired-state `CREATE TABLE`, call `dbDelta()` again" pattern already established by every other additive-column migration in this codebase (020-023). `dbDelta()`'s own idempotent schema-diffing makes one migration file correct for both databases: a database that already has `is_default` (ran 009/012 after the second correction) sees no schema difference and nothing happens; a database missing it (ran 009/012 before) gets `ALTER TABLE ... ADD COLUMN is_default TINYINT(1) NOT NULL DEFAULT 0`, which MySQL backfills onto every existing row - as required, treating every pre-existing row (English default or administrator-edited) as "possibly customized, never overwrite" rather than guessing. Migrations 009/012's own default-row `$wpdb->insert()` calls also gained the same ignored-return-value fix already applied to the repositories - a failed required seed write can no longer let those two migrations be recorded as complete.

**A sharper version of the same problem existed at the code-deployment level, not just the database level**: ELESYTH's migrations 001/002 must never run - and never be recorded as run - against a Core schema whose `is_default` column isn't actually in place yet, even in the narrow window right after a Core code update where the new code (and a passing `AME_MIN_CORE_VERSION` check) is already loaded but Core's own migrations 025/026 haven't executed on that particular request yet. Version compatibility alone cannot catch this - it answers "is this Core release new enough," not "has this Core release's migration actually finished running." Relying on `admin_init` hook-registration order between the two plugins is equally unsafe, since WordPress doesn't guarantee which of two plugins' same-priority `admin_init` callbacks fires first. Fixed by having ELESYTH's `Plugin::runPendingMigrations()` call Core's own `Migrator::installPending()` directly and synchronously, immediately before `ImplementationMigrator::installPending()` - not hook-order-dependent, and safe to call unconditionally on every invocation since it's already proven idempotent. Since `Plugin::activate()` delegates to `runPendingMigrations()`, this covers both the "both plugins already active, code-only update" case and the "ELESYTH activated before the first post-update `admin_init`" case the review named explicitly.

**Correction from a fourth independent review (also fixed before any of it was committed) - migrations 025/026 trusted `dbDelta()` without verifying it, and that gap was documented as manual-only instead of fixed**: `dbDelta()` has no reliable return value - it can silently fail to add a column on a real server (privileges, a locked table, a version quirk) with no PHP-visible error, and the third correction's migrations 025/026 would still be recorded as permanently complete by `MigrationRunner` if that happened, leaving the repositories' unconditional `is_default` references broken forever with no automatic retry possible. **The fix**: both migrations now query `SHOW COLUMNS FROM {table} LIKE 'is_default'` immediately after `dbDelta()` and throw `DatabaseWriteException` if the column isn't actually present - the same "verify, don't trust" pattern already applied to `$wpdb->insert()`/`update()` return values elsewhere in this history, applied here to `dbDelta()`'s lack of one.

Proving this required real test infrastructure, not just a claim: `FakeWpdb` (previously schema-blind) gained column-presence tracking, and the `dbDelta()` stub in `tests/bootstrap.php` (previously a pure no-op) now parses column names out of the `CREATE TABLE` SQL it's given and registers them - plus a one-shot `blockColumnAddition()` test hook (matching `failNextInsert()`/`failNextUpdate()`'s existing pattern) to simulate `dbDelta()` silently failing to add a specific column, which is what makes the postcondition check's *failure* path exercisable at all, not just its success path. Similarly, ELESYTH's cross-plugin migration-ordering guarantee (the previous correction, above) - previously described only as a code-review-verified, manually-staged claim - now has a real automated test (`PluginMigrationOrderingTest`) exercising the actual `Plugin::runPendingMigrations()` control flow against Core's real `Migrator::installPending()`, proving `ImplementationMigrator::installPending()` never runs when it throws.

Full reasoning for all four corrections: `docs/adr/024-elesyth-implementation-migrations.md`'s four addenda.

## 4. Release versioning and compatibility guard

Both plugins bumped to `0.3.0-alpha.1` as a single authoritative version constant (`AM_PLUGIN_VERSION` / `AME_PLUGIN_VERSION`), consistent WP headers (`Requires at least: 6.0`, `Requires PHP: 8.1`, matching `composer.json`'s `>=8.1` floor) added to both plugin files.

ELESYTH's compatibility guard (`Plugin::checkCoreCompatibility()`) no longer relies on `class_exists()` alone: it also requires `version_compare(AM_PLUGIN_VERSION, AME_MIN_CORE_VERSION, '>=')` (new constant `AME_MIN_CORE_VERSION`, currently `0.3.0-alpha.1`, hand-bumped whenever ELESYTH starts depending on something a specific Core release introduced). Failure produces a distinguishing `admin_notices` message ("Core not active" vs. "Core version too old, found X") and never fatals - `runPendingMigrations()` (both the `admin_init` and activation-hook paths) simply no-ops when incompatible.

## 5. Activation safety

Automated (unit-testable) coverage:
- `MigrationRunnerTest` (Core): proves two `MigrationRunner` instances under different option keys are genuinely isolated - via invocation-count tracking on each migration's `up()`, not just final-option-state assertion, so a real cross-contamination bug couldn't hide behind a passing assertion. Covers idempotency (same id never re-runs), default-option-key backward compatibility, **a failed migration `up()` is not recorded and is retried on the next run()**, and **a migration whose `up()` succeeds but whose tracking-option persistence (`update_option()`) fails is also not recorded and is retried**.
- `CertificateTemplateRepositoryTest`/`NotificationTemplateRepositoryTest` (Core): `save()` throws `DatabaseWriteException` on a failed insert or update; a failure partway through a batch of saves leaves earlier successful saves intact and the failed one unrecorded; a row inserted directly with `is_default = 1` (exactly like migrations 009/012 do) hydrates `isDefault = true`; `save()` always persists `isDefault = false` regardless of what's passed in, on both insert and update.
- `FieldDefinitionRepositoryTest`/`FieldMappingRepositoryTest` (Core): the same `save()`-throws-on-failed-insert/update coverage, added in the same pass that found these two repositories had the identical unchecked-`$wpdb`-return-value gap the template repositories did.
- `CertificateTemplateSeederTest`/`NotificationTemplateSeederTest` (ELESYTH): rewritten to model the **actual** sequence (Core's default row already present, via a `seedDefault()` test helper) rather than an empty repository - a fresh site (row still marked default) receives the Greek template; a legacy site with an administrator-edited row (row no longer marked default) is left completely untouched; a site where ELESYTH already seeded Greek content on an earlier request is not re-seeded; repeated activation is idempotent; a write failure partway through notification seeding leaves already-seeded templates alone and is fully completed on retry.
- `MemberFieldSeederTest`/`MemberPressFieldMappingSeederTest` (ELESYTH, new): existence-based create-if-missing behavior (no `is_default` concern here - Core never pre-populates these two tables) plus the same write-failure/retry coverage, against new `InMemoryFieldDefinitionRepository`/`InMemoryFieldMappingRepository` test doubles.
- `PluginCompatibilityTest` (ELESYTH): covers `Plugin::versionSatisfies()` (exact-match, newer-installed, older-installed, prerelease-vs-final-release ordering) and, via the extracted `Plugin::isCompatible(bool $coreActive, ?string $installedCoreVersion, string $minimumCoreVersion)` pure function, **the "Core not active at all" branch** - previously undocumented as untestable in this environment since Core's class is always genuinely loaded here via the path-repo dev dependency.
- `SeedDefaultTemplateMigrationsTest` (Core): loads migrations 009/012/025/026 directly (via `require`, the same mechanism `MigrationLoader` uses). 009/012: seed inserts throw `DatabaseWriteException` on a failed write, succeed with `is_default = 1` on the rows they create. 025/026 (extended with real postcondition coverage - see Section 3's fourth correction): succeed when the column already exists (`FakeWpdb::presetTableColumns()`); succeed when the column is newly added (the `dbDelta()` stub parses it out of the `CREATE TABLE` SQL and adds it); throw `DatabaseWriteException` when column addition is blocked (`FakeWpdb::blockColumnAddition()`, simulating `dbDelta()` silently failing); the failed migration is not recorded by `MigrationRunner`; a retry (the block being one-shot) succeeds and is recorded. All five cases covered for both migrations independently.
- `CertificateTemplateRepositoryTest`/`NotificationTemplateRepositoryTest` (Core, new case): a row saved with no `is_default` key at all hydrates as `isDefault = false` (the conservative choice) and a subsequent deliberate save persists a real `is_default = 0` going forward, with no PHP error either way.
- `PluginMigrationOrderingTest` (ELESYTH, new): exercises the real `Plugin::runPendingMigrations()` control flow against Core's real `Migrator::installPending()` (not a mock) and proves `ImplementationMigrator::installPending()` never runs - `ame_migrations`' tracking option is never touched - when `Migrator::installPending()` throws (triggered here by `AM_PLUGIN_DIR` being genuinely undefined in this unit-test process, which throws a real PHP `Error` before any database access).

Not automatable here (no live WordPress, no real MySQL) - **manual staging smoke-test checklist**:

## 6. Architecture constraints

Re-verified after all changes: no ELESYTH values, labels, templates, mappings, or policies were moved into Core. `grep -ril elesyth src/ database/` on Core returns only two illustrative code comments (`MigrationRunner.php`, and a pre-existing comment in `ImportersModule.php` from an earlier epic), both using ELESYTH only as an example of "an implementation plugin," not as actual logic or data. No automatic module discovery, new DI framework, new event bus, CQRS infrastructure, additional migration dependency, or frontend framework was introduced. Every Core change across all three correction rounds is generic, reusable infrastructure with no ELESYTH-specific content: `MigrationRunner`'s configurable option key; `DatabaseWriteException` and its use in four repositories plus migrations 009/012's own seed inserts; the `is_default` provenance column and its domain/repository support; migrations 025/026's additive schema fix. None of it encodes ELESYTH's Greek content, field labels, or policies - `is_default` is a generic "was this row deliberately written" flag any future implementation plugin could rely on the same way.

**New risk introduced by this task, not present before**: ELESYTH's `composer.json` now declares `artcom-ai/association-manager` as a **dev**-only dependency via a `path` repository, so PHPStan/PHPUnit can resolve Core's real classes during development. Verified with `composer install --no-dev` that this correctly excludes Core (and all dev tooling) from `vendor/` - but if a release build ever runs a bare `composer install` before zipping, the shipped plugin would bundle a duplicate copy of every `AssociationManager\Core\*` class, which fatals the moment both plugins are active together. This must become a standing step in whatever process builds the ELESYTH release zip.

## Remaining risks

1. The `composer install --no-dev` release-build requirement (Section 6) - a process step, not yet enforced by tooling. No build script exists in either repo to encode this automatically.
2. No real multi-plugin WordPress integration test exists for the full activation/compatibility/migration interplay - the *decision logic* (verify-then-throw in migrations 025/026; call Core's migrator first in ELESYTH's `Plugin::runPendingMigrations()`) now has real automated coverage (Section 3's fourth correction), but real `dbDelta()` behavior against a real MySQL/MariaDB server, and real WordPress `admin_init` hook timing across two real plugins, remain manual-staging-only - `FakeWpdb`'s column tracking is a pattern-matched simulation of this codebase's own `CREATE TABLE` SQL shape, not a real SQL engine.
3. `AME_MIN_CORE_VERSION` is hand-maintained, not derived from any machine-checked constraint - can drift if a future change forgets to bump it.
4. The stale untracked duplicate directory removal (Section 1) was flagged by this environment's destructive-action classifier; disclosed to the user, `git status` confirmed clean before and after, but worth a final human glance.
5. Correcting a shipped default template on sites that already have a row no longer marked `$isDefault` (an administrator edit, or ELESYTH's own earlier seed) is deliberately not something these seeders support - see `docs/MIGRATIONS.md`'s "Adding a new migration" section in the ELESYTH repo for the narrower, explicit mechanism required.
6. `DatabaseWriteException` is now thrown from every Core repository ELESYTH's four implementation migrations write through (`CertificateTemplateRepository`, `NotificationTemplateRepository`, `FieldDefinitionRepository`, `FieldMappingRepository`), plus migrations 009/012's own direct seed inserts, confirmed by an end-to-end audit of all four ELESYTH migrations. Other Core repositories unrelated to any implementation migration (e.g. `MemberRepository`) still call `$wpdb->insert()`/`update()` without checking the return value - out of scope for every review round so far, not audited or changed here.
7. `PluginMigrationOrderingTest` (ELESYTH) relies on `AM_PLUGIN_DIR` being genuinely undefined in that test process to make Core's real `Migrator::installPending()` throw - honestly representative of this test environment's actual gap (Core's own bootstrap file, which normally defines it, is never loaded here), but if a future test legitimately needs `AM_PLUGIN_DIR` defined for an unrelated reason, that addition would silently invalidate this test's premise (it would stop throwing, and the test would fail with "Expected ... to throw" rather than silently passing for the wrong reason - so this would be caught, not silently broken, but worth knowing about).
7. **Corrected**: an earlier version of this document (and of `docs/adr/024-elesyth-implementation-migrations.md`) claimed editing migrations 009/012 in place to add `is_default` was safe "because this plugin has never shipped a release." A third independent review found that claim false - development/staging/pilot databases can already have run those migrations under the original schema - and required the additive-migration fix (025/026) plus the cross-plugin migration-ordering fix described in Section 3 above. That false claim has been removed from both documents.
8. ELESYTH's `Plugin::runPendingMigrations()` now calls Core's `Migrator::installPending()` on every invocation before running its own migrations - cheap when Core's schema is already current (the common case), but this does mean every ELESYTH `admin_init` now also does Core's own migration-check work a second time redundantly with Core's own `admin_init` hook, on top of whatever Core's hook already did on the same request. Not measured for real-world overhead; acceptable at this scale (both are simple `get_option()`-gated checks) but worth revisiting if either plugin's migration list grows significantly.
