# ADR 024: Implementation-layer migrations (ELESYTH one-time seeding) + ELESYTH tooling baseline

## Status

Accepted

## Context

ADR-021 named two negative consequences up front: (1) ELESYTH's `admin_init`-based idempotent reseeding runs on every wp-admin page load, and (2) ELESYTH had no PHPUnit/PHPStan/PHPCS toolchain at all. Release 0.3-A's Stabilization Gate task required auditing both repositories without assuming the ADRs still matched the files on disk, and both gaps turned out to be worse in practice than "harmless at this scale":

`CertificateTemplateSeeder::seed()` and `NotificationTemplateSeeder::seed()` call an unconditional upsert-by-key `save()` on their repository. Wired to `admin_init` (as ADR-021 describes), this doesn't just re-run on every admin page load - it **silently reverts any admin edit to a certificate or notification template on the very next admin page load**, because "idempotent" for these two seeders means "always overwrite with ELESYTH's hardcoded copy," not "create if missing." (`MemberFieldSeeder` and `MemberPressFieldMappingSeeder` were already create-if-missing and never had this problem.) An admin editing a Greek notification template in wp-admin would see their change silently discarded the moment they (or anyone) loaded another admin page.

The Stabilization Gate's explicit constraints ruled out several tempting fixes: no new migration dependency, and the generic Core must not contain ELESYTH-specific migration logic.

## Decision

**Reuse Core's existing migration infrastructure (`MigrationInterface`, `MigrationLoader`, `MigrationRunner`) for ELESYTH's own one-time seed steps**, rather than inventing a second migration mechanism or writing ELESYTH-specific logic into Core.

The only Core change: `MigrationRunner`'s tracking-option key becomes a constructor parameter, defaulting to the exact same hardcoded value (`association_manager_migrations`) it always used. `new MigrationRunner()` behaves identically to before - this is additive and backward compatible, and it's generic infrastructure (an option key is not ELESYTH-specific knowledge), not a violation of "Core must not contain ELESYTH-specific migration logic."

**ELESYTH gets its own `ImplementationMigrator::installPending()`** (`src/ImplementationMigrator.php`), a small class that points `MigrationLoader` at ELESYTH's own `migrations/` directory (sibling to `src/`, mirroring Core's `database/migrations/` placement) and runs the result through `new MigrationRunner('ame_migrations')` - a tracking option entirely separate from Core's own, so the two plugins' migration bookkeeping can never collide or interact.

The four existing seeder calls became four migration files (`migrations/001_seed_certificate_templates.php` through `004_seed_memberpress_field_mappings.php`), each a thin wrapper calling the existing, unchanged seeder through its repository interface. **The seeders themselves were not touched** - `CertificateTemplateSeeder`/`NotificationTemplateSeeder` still unconditionally overwrite, but now that only happens once, ever, per migration id, not on every request. If ELESYTH ever needs to push a corrected template to already-provisioned sites, that's a new migration file with a new id (e.g. `005_...`), not a re-run of `001` - an admin's own edits made after the first run are never touched again by that migration.

`Plugin::seedContent()` (registered on `admin_init`) became `Plugin::runPendingMigrations()`, calling `ImplementationMigrator::installPending()`. The `admin_init` hook is kept (not replaced by activation-only) deliberately, mirroring Core's own `Kernel::registerHooks()` dual-hook pattern: it's what lets an already-active ELESYTH install pick up a new migration shipped in a code-only update, without requiring deactivate/reactivate. What changed is that `MigrationRunner` makes each individual migration id idempotent-by-skip, not idempotent-by-reapply - the mechanism that made the bug possible is gone, not just hidden behind a new check.

**`register_activation_hook()` was added to ELESYTH** (previously entirely absent), calling `Plugin::activate()` → the same `runPendingMigrations()` - so a fresh install gets its seed data immediately at activation instead of waiting for the first `admin_init`.

**Compatibility guard upgraded from `class_exists()` alone to a version check**: `Plugin::isCoreCompatible()` requires both `class_exists(CorePlugin::class)` and `version_compare(AM_PLUGIN_VERSION, AME_MIN_CORE_VERSION, '>=')`. `runPendingMigrations()` (both the `admin_init` and activation-hook paths) is a no-op if Core is missing or too old, rather than fataling - the admin sees a distinguishing `admin_notices` message ("Core not active" vs. "Core version too old") instead. `AME_MIN_CORE_VERSION` is a new constant in ELESYTH's bootstrap file, bumped by hand whenever ELESYTH starts depending on something a specific Core release introduced.

**ELESYTH now has the same PHPUnit/PHPStan(level 8)/PHPCS(WordPress-Extra) toolchain as Core**, closing ADR-021's second named gap. The one non-obvious piece: ELESYTH's `composer.json` adds a `path` repository pointing at `../association-manager` and requires `artcom-ai/association-manager` as a **dev** dependency only - this lets PHPStan/PHPUnit resolve Core's real classes (`AssociationManager\Core\Plugin`, the repository interfaces ELESYTH's migrations depend on) during local development and CI, without Core ever becoming a runtime dependency of the shipped plugin. **This has one sharp edge, documented here so it isn't rediscovered the hard way**: a plain `composer install` pulls Core's entire source tree into `vendor/artcom-ai/association-manager/`. If a release zip were ever built from that state, it would ship a second, duplicate copy of every `AssociationManager\Core\*` class - which fatals ("Cannot declare class ... because the name is already in use") the moment both plugins are active together, since PHP would try to load the same class from two different plugin directories. **Every ELESYTH release build must run `composer install --no-dev` (verified: this correctly drops `artcom-ai/association-manager` and every other dev tool from `vendor/`) before zipping.** See `docs/releases/RELEASE-0.3-ALPHA-1-STABILIZATION.md` for this as a standing manual check, not just a one-time note here.

New unit coverage: `MigrationRunnerTest` (Core) proves two `MigrationRunner` instances under different option keys are genuinely isolated (via invocation-count tracking, not just final-state assertion - a same-id migration under two different runners must both actually execute). `PluginCompatibilityTest` (ELESYTH) covers the `version_compare()` decision (`versionSatisfies()`, pulled out of `isCoreCompatible()` specifically so it's testable against arbitrary version strings, since the real constants it reads can't be redefined per test case) - equal versions, newer-installed, older-installed, and the prerelease-vs-final-release ordering ELESYTH will rely on once it ships past `-alpha.1`. The `class_exists(CorePlugin::class)` branch itself (Core genuinely absent) isn't unit-tested - Core is always loaded in the test process via the path-repo dev dependency - and is covered by the manual staging smoke-test checklist instead.

## Consequences

Positive:

- The actual bug (admin template edits silently reverted) is fixed at its root: each seed step now runs at most once per install, ever, tracked the same proven way Core's own schema migrations already are.
- Zero new migration mechanism, zero ELESYTH-specific code in Core - `MigrationRunner`'s one new constructor parameter is the entire Core-side footprint, and it's generic (any future Implementation can reuse the exact same pattern with its own option key and `migrations/` directory).
- ELESYTH now has a real, enforced quality bar (`composer validate`/`test`/`stan`/`cs`, all green) instead of "verified with `php -l` and a manual smoke test" (ADR-021's own words for what came before).
- The Core-version compatibility guard means an ELESYTH site can no longer silently run against a Core release too old to have the interfaces/methods ELESYTH's migrations need - it gets a clear admin notice instead of an undefined-method fatal buried in a migration's `up()`.

Negative:

- The path-repo dev-dependency approach for ELESYTH's tooling introduces the `--no-dev` build requirement described above - a new, easy-to-forget step in the release process. This is a real remaining risk (see the release doc's Remaining Risks section), not fully eliminated by this ADR, only documented and verified as reproducible.
- No real WordPress multi-plugin integration test exists for the activation/compatibility/migration interplay (fresh Core activate → ELESYTH activate → repeated activation → Core upgrade → ELESYTH admin_init self-heal) - covered by unit tests where the logic is pure (`versionSatisfies()`, `MigrationRunner` isolation) and by a manual staging checklist everywhere else, same category of gap ADR-021 already accepted for WP-glue code generally.
- `AME_MIN_CORE_VERSION` is a hand-maintained constant, not derived from anything machine-checked (e.g. a Composer version constraint) - it can drift out of sync with what ELESYTH's code actually requires if a future change forgets to bump it.

## Addendum: upgrade safety, write-failure semantics, testability (independent Release 0.3 review)

An independent review of the above design found three real gaps before it shipped. All three are fixed; none required a new mechanism, an ELESYTH-specific Core change, or a design redo.

**1. Fresh-install vs. legacy-upgrade seeding.** As designed above, migrations `001`/`002` called `CertificateTemplateSeeder`/`NotificationTemplateSeeder` unchanged - both still did an unconditional upsert. That's harmless the very first time a migration ever runs on a brand-new site (no row exists yet, so "overwrite" just means "create"). But an ELESYTH site that had already been running the *old*, pre-this-ADR `admin_init`-reseed-forever code has template rows already sitting in the database, and that site's `ame_migrations` option doesn't exist yet either (it's new). On upgrade, migrations `001`/`002` would see "not yet recorded as executed" and run once - correctly, per the tracking mechanism - but that one run would still silently overwrite whatever's currently in that row, admin-edited or not, because the seeders themselves never checked.

Fix: **`CertificateTemplateSeeder::seed()` and `NotificationTemplateSeeder::seed()` are now create-if-missing**, using the repository's existing `find()` method (`CertificateTemplateRepositoryInterface`/`NotificationTemplateRepositoryInterface` both already exposed it) - if a row already exists for that key, `seed()` returns without calling `save()` at all. No content comparison, no "does this look administrator-edited" heuristic - existence alone decides, per the review's explicit instruction not to infer intent from content.

- **Fresh install**: no rows exist yet → `find()` returns null → the row is created. ELESYTH's default Greek content is what a new site gets.
- **Legacy upgrade** (a site that ran the old always-overwrite code and is only now getting `ame_migrations` for the first time): rows already exist → `find()` returns non-null → `seed()` no-ops for that key, leaving whatever's currently stored (default or administrator-edited) exactly as it was.
- Because the check is per-key (per `type_key` for certificates, per `(event_key, channel)` for notifications, checked independently inside the loop), a site can be in a mixed state - some templates administrator-edited and preserved, others still missing and freshly seeded - and each is handled correctly on its own.

**2. Write failures were silently swallowed.** `CertificateTemplateRepository::save()` and `NotificationTemplateRepository::save()` called `$wpdb->insert()`/`$wpdb->update()` without checking the return value - both calls return `false` on a real DB failure, which was simply discarded. Because `MigrationRunner::run()` records a migration as executed immediately after its `up()` returns (see the original decision above), a migration whose `up()` silently ignored a failed write would still get recorded as successfully complete.

Fix: both `save()` methods now check the insert/update return value and throw a new, generic `AssociationManager\Database\DatabaseWriteException` (`src/Database/DatabaseWriteException.php`) when it's `false`. This is Core infrastructure, not ELESYTH-specific - any repository can use it. Letting the exception propagate out of a migration's `up()` is what keeps `MigrationRunner` from recording that id: the `foreach` loop in `run()` aborts before reaching `$executed[] = $migration->id()`, so the next `run()` call (the next `admin_init`, or a manual retry) attempts that same migration again. This falls out of `MigrationRunner`'s existing control flow with zero new exception handling needed there - the fix is entirely in the repositories throwing instead of swallowing.

Because `NotificationTemplateSeeder::seed()` loops over 7 templates and (per point 1) is now create-if-missing, a write failure partway through the loop is naturally retry-safe: whichever templates already saved before the failure are found on retry and skipped, and only the templates still actually missing (including the one that just failed) are attempted again. No separate transaction or rollback logic was needed for this - create-if-missing plus per-item persistence already gives idempotent retry for free.

**3. `MigrationRunner` ignored `update_option()`'s return value.** Even with `up()` succeeding and throwing correctly on any write failure inside it, `MigrationRunner::run()` still called `update_option( $this->optionKey, $executed, false )` without checking whether *that* write succeeded - a WordPress options-table failure at exactly that moment would mean the migration's actual work (e.g. rows inserted) happened, but the bookkeeping never recorded it, and worse, the code proceeded as if it had.

Fix: `run()` now checks `update_option()`'s return value and throws `DatabaseWriteException` if it's `false`. `update_option()` returning `false` normally has two possible causes - a genuine write failure, or WordPress detecting the new value is identical to the old one and skipping the write as a no-op. This call site can only ever hit the first case: `$executed` always has exactly one more element than it did before (a freshly-appended id), so the "new value equals old value" no-op case is structurally impossible here. Treating every `false` as a real failure is therefore safe, not overcautious - documented inline in `MigrationRunner::run()`.

**Testability.** `Plugin::isCoreCompatible()` (ELESYTH) previously read `class_exists(CorePlugin::class)` and the real `AM_PLUGIN_VERSION` constant directly, which the original ADR text above noted as the one branch (`Core not active at all`) that couldn't be unit tested in this environment - Core's class is always genuinely loaded in the test process via the path-repo dev dependency, so `class_exists()` is always true here regardless of what a real deactivated-Core scenario would produce. Extracting `Plugin::isCompatible(bool $coreActive, ?string $installedCoreVersion, string $minimumCoreVersion): bool` as a pure function removes that limitation: tests now pass `$coreActive = false` directly, exercising the exact branch that was previously undocumented-as-untestable. `isCoreCompatible()` itself is unchanged in behavior, just now a thin wrapper passing real values into the pure function.

**New Core test coverage**: `CertificateTemplateRepositoryTest`/`NotificationTemplateRepositoryTest` (`save()` throwing on failed insert/update, plus a partial-failure-mid-loop regression test), `MigrationRunnerTest` (a failed `up()` is not recorded and is retried; a failed `update_option()` is not recorded and is retried, even though `up()` itself succeeded). `tests/Support/FakeWpdb.php` gained `failNextInsert(string $table)`/`failNextUpdate(string $table)` test-only hooks; `tests/bootstrap.php`'s `update_option()` gained a similar per-key one-shot failure toggle (`TestCase::failNextUpdateOptionFor()`).

**New ELESYTH test coverage**: `CertificateTemplateSeederTest`/`NotificationTemplateSeederTest` (fresh-install creates, legacy-upgrade-style existing row is preserved verbatim including administrator-edited content, partial-failure-then-retry completes only the still-missing templates) against new in-memory repository doubles (`tests/Support/InMemoryCertificateTemplateRepository.php`, `InMemoryNotificationTemplateRepository.php` - the interfaces are small enough that hand-written fakes were simpler than wiring `FakeWpdb`/Core's real repositories into ELESYTH's own test process). `PluginCompatibilityTest` gained the four `isCompatible()` branch tests described above.

**What remains manual-only**: the actual multi-plugin WordPress activation sequence (Core activate → ELESYTH activate → an upgrade from the pre-migration code with real admin-edited template rows in a real database → confirming the edit survives) is still not exercised by any automated test - the fixes above make the *logic* correct and unit-verifiable, but a real `$wpdb`, real WordPress plugin loading order, and a genuinely pre-existing database row from an older code version are still staging-only concerns. See the release document's manual smoke-test checklist, which now includes an explicit legacy-upgrade-with-edited-template scenario.

**Operational note**: refreshing ELESYTH's mirrored copy of Core in `vendor/artcom-ai/association-manager` after a Core-side change does not reliably happen via `composer update artcom-ai/association-manager` alone (observed during this fix: it reported "Nothing to modify" despite Core's files having changed). `rm -rf vendor/artcom-ai && composer install` reliably picks up the change. This only affects local development/CI against an unpublished Core branch, not the shipped plugin (which never has `vendor/artcom-ai` at all - see Section 6 of the release document).

## Addendum: the fresh-install model was still wrong (second independent review)

The first addendum above (create-if-missing certificate/notification seeders) was itself built on a false premise, caught by a second independent review: **it assumed a genuinely empty repository is what "fresh install" looks like the first time these seeders run.** It never is. Core's own `009_create_notification_templates_table.php` and `012_create_certificate_templates_table.php` migrations insert English default rows for most of these templates as part of *creating the table* - and Core's migrations always run before ELESYTH's, on every site, because ELESYTH requires Core to already be active. So `CertificateTemplateSeeder`/`NotificationTemplateSeeder`'s `find() !== null` check (the first addendum's fix) was true on literally every site, fresh or legacy, and the seeders never actually seeded anything - the bug this whole ADR exists to fix (templates staying in English/reverting) was **not actually fixed** by the first addendum, only its most obviously-broken symptom (unconditional overwrite) was.

**Why existence and content can't resolve this, stated plainly (per the review's explicit instruction not to proceed without this):** the moment `001_seed_certificate_templates` first runs on any site, a row already exists. There is no persisted signal that distinguishes "this row is still exactly what Core's migration inserted, nothing has touched it since" from "an administrator already customized this" - both states look identical from `find()`'s return value alone. Comparing the row's *text* against Core's known English default was considered and rejected: Core's default copy is free to change across releases (breaking the comparison silently for every site already on an older default), and there is no way to tell an administrator's edit that happens to coincide with Core's default apart from a row nobody ever touched - the review's own instruction was explicit that text comparison must not be used to infer this.

**The fix**: an explicit, non-content provenance flag. `certificate_templates`/`notification_templates` gained an `is_default TINYINT(1) NOT NULL DEFAULT 0` column, added directly to migrations 009/012's own `CREATE TABLE` statements (not a new later migration - see below for why that specifically doesn't work here) and set to `1` only on those migrations' own direct `$wpdb->insert()` calls. `CertificateTemplate`/`NotificationTemplate` gained a matching `bool $isDefault = false` property. `CertificateTemplateRepository`/`NotificationTemplateRepository::save()` always persist `is_default = 0`, regardless of what's passed in - the repository is the "someone is deliberately writing this" path, whether the caller is an administrator's admin-UI submission or an implementation plugin's own seeder, and either one permanently ends a row's "untouched default" status. ELESYTH's seeders now seed when `find()` returns null **or** returns a template with `isDefault === true`; they skip when it returns a template with `isDefault === false`.

**Migrations 009/012 were edited in place to add the column** (rather than adding it purely via a later migration) so that a genuinely fresh install gets `is_default` from the very first time those migrations ever run, with the correct rows already flagged `1`. **This edit, by itself, was incomplete and briefly documented as safe on a false premise - corrected by a third independent review, see the fourth addendum below.** In short: any database where 009/012 had already run *before* this edit shipped does not have the `is_default` column at all (`MigrationRunner` never re-runs a completed migration id, so editing an already-executed migration's file has no effect on a site that already ran it) - yet the revised repositories unconditionally read and write `is_default`, which fails against such a database. A fourth, additive migration was required to close this gap; see below.

**Consequence for `MemberFieldSeeder`/`MemberPressFieldMappingSeeder`**: unaffected. Core never ships default field definitions or field mappings of its own (those tables start genuinely empty for Core), so the ambiguity that motivated `is_default` does not exist for them - plain existence (`find() !== null`) remains a correct, sufficient signal, confirmed by re-reading both seeders' own docblocks, which already said as much.

**Second Core gap found and fixed in the same pass, unrelated to the fresh-install bug**: `FieldDefinitionRepository::save()` (used by migration 003) and `FieldMappingRepository::save()` (used by migration 004) had the exact same ignored-`$wpdb`-return-value bug `CertificateTemplateRepository`/`NotificationTemplateRepository::save()` had before the first addendum fixed it - both now throw `DatabaseWriteException` on a failed insert/update, for the same reasons. All four of this repo's implementation migrations were re-audited end-to-end for this class of bug afterward: each migration's `up()` only ever calls `find()`/`save()` on its one repository interface, no other raw write path exists, so this is now a complete accounting across all four, not a partial one.

**New test coverage**: Core - `CertificateTemplateRepositoryTest`/`NotificationTemplateRepositoryTest` gained `is_default` hydration and save-always-clears-it tests (seeding a raw row via `$wpdb->insert()` with `is_default = 1`, exactly as migrations 009/012 do); `FieldDefinitionRepositoryTest`/`FieldMappingRepositoryTest` gained the same insert/update-failure tests the template repositories already had. ELESYTH - `CertificateTemplateSeederTest`/`NotificationTemplateSeederTest` were rewritten to model the actual sequence (a Core-default row seeded first via a new `seedDefault()` test helper, then the seeder run against it) instead of an empty repository, with explicit fresh-site, legacy-edited-site, already-Greek-site, and repeated-activation-idempotency cases; new `MemberFieldSeederTest`/`MemberPressFieldMappingSeederTest` cover the same existence-based create-if-missing behavior plus write-failure/retry, using new `InMemoryFieldDefinitionRepository`/`InMemoryFieldMappingRepository` test doubles.

**Still not covered by anything automated**: the real end-to-end sequence on a live site (Core's migration 009/012 genuinely inserting a row via real MySQL, then ELESYTH's migration 001/002 genuinely reading it back with `is_default = 1` through the real `$wpdb`) - the unit tests above prove the *logic* is correct given an `is_default` value however it arrived, but not that Core's raw insert and ELESYTH's repository read agree on what that column means in a real database. This is the same category of WP-glue gap already accepted throughout this codebase (ADR-015) and belongs on the manual staging checklist, not invented as a new automated-test claim.

## Addendum: the schema rollout itself was not upgrade-safe (third independent review)

A third independent review caught that the second addendum's fix, while correctly *designed*, was **incorrectly claimed to be safe to ship as-is** on the reasoning "this plugin has never shipped a release, so no database exists without the new column." That reasoning does not hold: "never shipped a public release" is not the same as "no database anywhere has ever run these migrations" - any development, staging, or the ELESYTH pilot's own environment that had already activated Core before this fix landed already has `009_create_notification_templates_table`/`012_create_certificate_templates_table` recorded as executed, under the *original* schema (no `is_default` column). `MigrationRunner` never re-runs a completed migration id - editing 009/012's file content has no retroactive effect on such a database. Yet the revised `CertificateTemplateRepository`/`NotificationTemplateRepository` unconditionally reference `is_default` in every `SELECT`/`INSERT`/`UPDATE`, which fails with a real MySQL "Unknown column" error the moment either runs against that database. The review was explicit: this claim had to be removed and the real gap fixed, not just documented as a risk.

**The fix: two new, purely additive migrations**, `025_add_is_default_to_notification_templates_table.php` and `026_add_is_default_to_certificate_templates_table.php` - the next available Core migration ids, following the exact same "repeat the full desired-state `CREATE TABLE` and call `dbDelta()` again" pattern already established by every other additive-column migration in this codebase (020, 021, 022, 023; see 021's own comment: "same full-desired-schema dbDelta() pattern as migration 020"). `dbDelta()` is schema-diffing and idempotent, which is what makes a single migration file correct for both databases it needs to cover without any conditional logic of its own:

- **A database where 009/012 already ran under the *revised* schema** (is_default already exists, with `1` on the rows those migrations inserted): `dbDelta()` compares the given `CREATE TABLE` against the actual table, finds no difference, and does nothing. The existing `is_default = 1` rows are untouched.
- **A database where 009/012 ran under the *original* schema** (is_default is missing entirely): `dbDelta()` issues `ALTER TABLE ... ADD COLUMN is_default TINYINT(1) NOT NULL DEFAULT 0`. MySQL backfills every existing row - an English default nobody ever touched, or an administrator's edited Greek content, there is no way to tell which - to `is_default = 0`. This is the deliberately conservative choice the review required explicitly ("Existing/legacy rows must become is_default = 0, preserving all rows as potentially administrator-edited"): every pre-existing row is treated as possibly customized and is never a seeding target again, rather than guessing from content.

**A second, related gap in the same area**: migrations 009/012's own default-row `$wpdb->insert()` calls (the ones that set `is_default = 1`) still ignored a failed insert's `false` return value - the same class of bug fixed in the repositories by the first addendum, just not yet applied to these two migrations' own raw writes. Both now check the result and throw `DatabaseWriteException` on failure, so a failed required seed write can no longer let `MigrationRunner` record 009/012 as complete.

**Migration ordering / readiness across the two plugins**: the review raised a sharper version of the same problem at the *code-deployment* level, not just the *database* level. `ame_migrations`' migrations `001_seed_certificate_templates`/`002_seed_notification_templates` must never run - and, critically, must never be *recorded* as having run - before Core's own schema (specifically, the `is_default` column) is actually in place, even during the narrow window right after a Core code update where the new code (and therefore a passing `AME_MIN_CORE_VERSION` version check) is already loaded but Core's own pending migrations (025/026) have not executed yet on that particular request. `Plugin::isCoreCompatible()`'s version check cannot catch this by itself - it answers "is this Core release new enough," not "has this Core release's database migration actually finished running yet," and those are genuinely different questions once a Core update ships a migration ELESYTH's own migrations depend on. Relying on `admin_init` hook registration order between the two plugins to guarantee Core's hook fires first is equally unsafe - WordPress does not guarantee which of two different plugins' same-priority `admin_init` callbacks runs first; it depends on plugin load order, which neither plugin controls.

**Fix**: `Plugin::runPendingMigrations()` (ELESYTH) now calls `AssociationManager\Database\Migrator::installPending()` - Core's own top-level migration entry point, the same one `Kernel::registerHooks()` itself calls on Core's `admin_init` - explicitly and synchronously, immediately before `ImplementationMigrator::installPending()`. This does not depend on hook ordering at all: it is a direct function call, so Core's migrations (including 025/026) are guaranteed to have finished, on that same request, before ELESYTH's own migrations 001-004 ever touch a Core table. It is safe to call unconditionally on every `runPendingMigrations()` invocation (both the `admin_init` path and the `register_activation_hook`-driven `activate()` path, since `activate()` delegates to `runPendingMigrations()`) because `Migrator::installPending()` was already proven idempotent - already-executed migration ids are skipped (`MigrationRunnerTest`) - so this adds no meaningful cost on the overwhelmingly common case where Core's schema is already current.

This covers both scenarios the review named explicitly: **a code-only update where both plugins are already active** (the next `admin_init` on either plugin - or a cron/CLI request that happens to trigger ELESYTH's hook - now brings Core's schema current before ELESYTH's own migrations run, regardless of which plugin's hook WordPress happened to fire first) and **ELESYTH activated before the first `admin_init` following a Core code update** (`Plugin::activate()` → `runPendingMigrations()` → `Migrator::installPending()` runs Core's pending migrations synchronously as part of ELESYTH's own activation, before `ImplementationMigrator::installPending()` ever runs).

**Required regression scenarios and their coverage**:
1. *Clean Core database*: `SeedDefaultTemplateMigrationsTest` runs migrations 009/012 directly (via `require`, the same mechanism `MigrationLoader` uses) against `FakeWpdb` and confirms every seeded row has `is_default = 1`; `CertificateTemplateSeederTest`/`NotificationTemplateSeederTest` confirm ELESYTH's seeders replace an `is_default = 1` row with Greek content and clear the flag.
2. *Legacy Core database*: `CertificateTemplateRepositoryTest`/`NotificationTemplateRepositoryTest` gained `testFindTreatsARowMissingTheIsDefaultKeyEntirelyAsNotDefault` - a row saved with no `is_default` key at all hydrates as `isDefault = false`, and a subsequent deliberate save persists a real `is_default = 0` going forward. `SeedDefaultTemplateMigrationsTest` additionally now exercises 025/026 themselves against a simulated legacy (column-missing) table - see the fourth addendum below for the column-simulation mechanism this required.
3. *Core code updated but the additive migration not yet run*: `PluginMigrationOrderingTest` (ELESYTH) exercises the real `Plugin::runPendingMigrations()` control flow and proves `ImplementationMigrator::installPending()` never runs when `CoreMigrator::installPending()` throws - see the fourth addendum below.
4. *Repository save after legacy upgrade*: same `testFindTreatsARowMissingTheIsDefaultKeyEntirelyAsNotDefault` tests above cover "deliberate saves persist `is_default = 0`." "No unknown-column database error" against a *real* MySQL server is still not something `FakeWpdb` can verify (see the fourth addendum for what changed here and what still can't be simulated) - but migrations 025/026 no longer merely trust `dbDelta()` silently; see below.

## Addendum: dbDelta() has no reliable return value - migrations 025/026 didn't verify their own postcondition (fourth independent review)

A fourth independent review found that migrations 025/026, as shipped in the third addendum above, called `dbDelta()` and then simply trusted it had added the column - `dbDelta()` has no reliable return value to check, and can legitimately fail to add a column on a real server (insufficient DB privileges, a locked table, a MySQL/MariaDB version quirk in how `dbDelta()` diffs schema) without raising any PHP-visible error. If that happened, the migration's `up()` would still return normally, `MigrationRunner` would record it as executed forever, and the repositories' unconditional `is_default` references would keep failing with real "Unknown column" errors on every subsequent request - permanently, since the migration id would never be retried. The review was explicit: documenting this as a manual-only limitation was not acceptable; an automated postcondition check was required.

**The fix**: both migrations now query `SHOW COLUMNS FROM {table} LIKE 'is_default'` immediately after calling `dbDelta()` and throw `DatabaseWriteException` if the column isn't actually there - the same "verify, don't trust" pattern already used for `$wpdb->insert()`/`update()` return values elsewhere in this ADR's history, applied to `dbDelta()`'s lack of one.

**Making this genuinely testable required extending `FakeWpdb` with real (if still pattern-matched, not a real SQL engine) column tracking** - previously it had none at all. `tests/bootstrap.php`'s `dbDelta()` stub, previously a pure no-op, now parses the column names out of the `CREATE TABLE` statement it's given (skipping `PRIMARY`/`UNIQUE`/`KEY`/`CONSTRAINT`/`INDEX`/`FOREIGN` lines) and registers them against `FakeWpdb` via a new `applyCreateTableColumns()` method. `FakeWpdb` gained `get_row()` support for the `SHOW COLUMNS FROM ... LIKE '...'` query shape (checked before the generic `SELECT`/`WHERE` path, since that path would otherwise misinterpret it as a data query and return an unrelated row), plus three test-only hooks: `presetTableColumns()` (model a table that already has a column, e.g. a clean install where 009/012 already created it), `blockColumnAddition()` (one-shot, matching `failNextInsert()`/`failNextUpdate()`'s existing pattern - the *next* attempt by the `dbDelta()` stub to add a specific column to a specific table is silently refused, modeling a real `dbDelta()` failure), and `hasColumn()` (assertion helper).

**New Core test coverage** (`SeedDefaultTemplateMigrationsTest`, replacing the previous smoke-test-only coverage for 025/026): column already exists (`presetTableColumns()`, migration succeeds, no-op) - covers regression scenario 1 (clean database) directly at the migration level, not just via the repositories; column is newly added (no preset, the `dbDelta()` stub adds it, migration succeeds) - covers regression scenario 2 (legacy database gaining the column); column addition is blocked (`blockColumnAddition()`, migration throws `DatabaseWriteException`); the failed migration is not recorded by `MigrationRunner` (`get_option()` on its tracking option stays empty); a retry (the one-shot block having been consumed by the first attempt) succeeds and is recorded. All five cases are covered for both migration 025 and migration 026 independently.

**New ELESYTH test coverage** (`PluginMigrationOrderingTest`, addressing regression scenario 3, previously undocumented as untestable): exercises the real `Plugin::runPendingMigrations()` - Core's real `Migrator::installPending()` (loaded via the composer path-repository dev dependency) is genuinely invoked, not mocked. It's made to throw via a real, honestly-described precondition gap in this specific unit-test process: `AM_PLUGIN_DIR` (the constant Core's own bootstrap file normally defines) is never defined in ELESYTH's `tests/bootstrap.php`, since nothing else in this suite needs it - referencing it inside `Migrator::installPending()` throws a PHP `Error` before any database access is attempted. The test proves `ImplementationMigrator::installPending()` never runs afterward (`ame_migrations`' tracking option is never touched) - if a future change wrapped the `CoreMigrator::installPending()` call in a `try`/`catch` that swallowed the error and continued, this test would fail.

**What still cannot be simulated, honestly**: `FakeWpdb`'s column tracking (and the `dbDelta()` stub feeding it) is a pattern-matched simulation of *this codebase's own* `CREATE TABLE` SQL shape, not a real SQL engine or a real `dbDelta()` - it proves the migrations' *logic* is correct (call `dbDelta()`, then verify, then throw or proceed accordingly) given whatever `dbDelta()` did, but it cannot prove real `dbDelta()`'s actual behavior against a real MySQL/MariaDB server, and it cannot prove a real "Unknown column" SQL error is avoided end-to-end (`FakeWpdb` has never modeled column constraints at all - a query referencing a nonexistent "column" would simply return an absent array key, not error, whether or not this fix exists). Similarly, `PluginMigrationOrderingTest` proves the *control-flow guarantee* (a thrown exception short-circuits the second call) but not that a real Core code update's real pending migration is genuinely absent/present at the moment WordPress fires either plugin's real `admin_init`. Both remain on the manual staging checklist for that reason - the difference from before this addendum is that the *decision logic* (verify-then-throw; call Core's migrator first) now has real, meaningful automated coverage, not just documentation of an untested design.
