# ADR 023: Admin-managed field definitions

## Status

Accepted

## Context

Field *definitions* (`Core\Fields\FieldDefinition` - what fields exist, their type/label/visibility) had only ever been registered in PHP code against `FieldRegistry`, by a Module or a per-client implementation calling `register()` at boot time. Field *values* (`wp_am_field_values`, migration 006) were already admin-editable per-member via `EditMemberPage`, but the set of fields itself required a code change and a deploy to alter. Once ELESYTH had real imported data and a real staging feedback loop, this stopped being acceptable - the explicit ask was "how does the admin create the fields" followed by "I want you to create it, I find it important," plus a request to recreate field definitions directly from the real MemberPress data already flowing through the Importer built earlier this session.

**Classification: Core**, not Module or Implementation. Field definitions are Core's own concept (`Core\Fields\FieldDefinition`/`FieldRegistry` already lived there); making them admin-manageable is infrastructure any association benefits from, the same way `Core\Fields\Admin\FieldRenderer` already was. `Modules\Importers\FieldMappingRegistry` (a different, Importers-owned concept - which *source* key maps to which field) got the identical treatment for the same reason, staying in Importers rather than moving to Core.

## Decision

**Two new tables, one per existing in-memory registry**: `wp_am_field_definitions` (migration 018) and `wp_am_field_mappings` (migration 019) - both purely additive, matching this project's standing migration discipline. Neither registry (`FieldRegistry`, `FieldMappingRegistry`) changed shape or its consumers' code at all - `FieldValueService`, `DirectoryService`, `PortalService`, `MemberImportService` still just call `FieldRegistry::forEntityType()`/`FieldMappingRegistry::forSource()` exactly as before. The only new thing is *where the registries get populated from*.

**Boot-time loading is deferred to `init` at priority 5** (`CoreServiceProvider`/`ImportersModule`), not run synchronously during `Kernel::boot()`. `boot()` runs on every request starting at `plugins_loaded`, before `admin_init` has had a chance to apply a just-added migration on a fresh activation - querying the new tables that early risks hitting them before they exist. Priority 5 keeps this ahead of `Kernel::registerHooks()`'s default-priority `association_manager_loaded` (used by implementations), though in the end state that ordering no longer matters much since ELESYTH stopped registering fields/mappings in code at all (see below).

**Upsert-by-key repositories, hand-written find-then-insert-or-update** (`FieldDefinitionRepository`, `FieldMappingRepository`) - the same pattern `NotificationTemplateRepository`/`CertificateTemplateRepository` already established, not a raw `INSERT ... ON DUPLICATE KEY UPDATE`. Raw prepared `INSERT` doesn't correctly express SQL `NULL` for nullable numeric placeholders (`%d`/`%f` coerce a PHP `null` to `0`), while `$wpdb->insert()`/`update()` handle `null` in the data array correctly - both repositories have several nullable numeric columns (`min_length`, `max_value`, etc.), so this wasn't optional.

**A new admin page, `Core\Fields\Admin\FieldDefinitionsPage`**, list-then-edit-one (same shape as `CertificateTemplatesPage`/`NotificationTemplatesPage`): create, edit, delete. Deliberately fixed to the `"member"` entity type for this pass - it's the only entity type anything in this codebase actually uses (Directory/Portal/Importers all hardcode it); parameterizing the page for other entity types later is trivial, not a redesign, so it wasn't built speculatively now. A field's `key` is immutable once created (shown read-only on the edit form) - renaming it would silently orphan every already-stored value under the old key, a real data-loss footgun not worth the convenience.

**Deleting a field cascades to its stored values** (`FieldValueRepositoryInterface::deleteForField()`, new) - an admin explicitly confirms this in the UI (a JS `confirm()` on the delete button) rather than leaving orphaned `wp_am_field_values` rows under a key nothing references anymore.

**"Recreate fields from MemberPress" reuses the existing dry-run wholesale**, adding no new source-scanning logic: `FieldDiscoveryService::createFieldsFromUnmappedKeys()` is handed `ImportSummary::allUnmappedKeys()` - the exact same list the Import page's report already computes and shows. For each key with no existing mapping yet, it creates a plain-text, admin-only-visibility `FieldDefinition` plus a `FieldMapping`, using a best-effort humanized label (strip a `mepr-`/`mepr_` prefix, replace remaining separators with spaces, title-case). This is explicitly a **starting point**, not a finished configuration - the admin is expected to review and correct labels/types/visibility via the Member Fields page afterward, especially since a source key that's itself a transliteration (e.g. `eidikotita`) doesn't become correct Greek by title-casing it. Source-key hyphens are converted to underscores when deriving the field key (`mepr-tilefono-epikoinonias` → `mepr_tilefono_epikoinonias`), not stripped - stripping would have collapsed real ELESYTH meta keys into unreadable runs like `meprtilefonoepikoinonias`.

**Seeding semantics split deliberately in two, by whether the seeded thing is meant to be admin-edited afterward.** `CertificateTemplateSeeder`/`NotificationTemplateSeeder` (existing, unchanged) always overwrite on every `admin_init`, so ELESYTH's canonical copy stays in sync with future plugin releases - by design, an admin edit to those templates would already be repeatedly reset today. The new `MemberFieldSeeder`/`MemberPressFieldMappingSeeder` do the opposite: create-if-missing only, never overwrite - since the entire point of this ADR is that fields become admin-editable, a seeder that reset them on every page load would silently undo the feature. ELESYTH's `Plugin::boot()` no longer calls `FieldRegistry::register()`/`FieldMappingRegistry::register()` directly at all (the old `association_manager_loaded` hooks were removed) - `MemberFieldDefinitions::all()`/`MemberPressFieldMappings::all()` are now purely seed data, consumed once per field/mapping's lifetime, not re-registered into memory on every request.

## Consequences

Positive:

- An admin can now add, edit, or remove a member field entirely from wp-admin - no code change, no deploy, closing the exact gap raised.
- "Recreate fields from MemberPress" turns the earlier dry-run's long, previously only-informational "unmapped source fields" list into real, immediately-usable fields with one click - directly closing the loop from the real 531-member import.
- Zero changes to any existing consumer of `FieldRegistry`/`FieldMappingRegistry` - the entire admin-manageability layer sits behind the same two registries every other module already depended on.
- 21 new tests (repository CRUD/upsert round-trips for both new tables, `FieldValueRepository::deleteForField()`, `FieldDiscoveryService`'s key-sanitization/humanization/skip-if-already-mapped behavior) - 237 total, all passing.
- A real `FakeWpdb::update()` bug surfaced and got fixed in the process: it only ever matched `WHERE id = ...`, silently crashing on any repository (like these two new ones) using a composite WHERE clause - a genuine gap in the shared test double, not a workaround.

Negative:

- Auto-generated field labels from "recreate from MemberPress" are not real translations - for ELESYTH specifically, most raw MemberPress meta keys are themselves Greek transliterations (`eidikotita`, `tilefono`), and title-casing a transliteration doesn't produce the correct Greek word. Every auto-created field needs a human pass before being trusted as a real "Ειδικότητα"-quality label.
- No reordering/drag-drop UI for `display_order` - a plain number input on the edit form. Acceptable for the handful of fields expected in practice; would need real UI work if a future association wants dozens of fields.
- ~~The Member Fields page's "Options" input (for `TYPE_SELECT`) is a plain `value|Label` per-line textarea, not a proper repeater UI~~ - superseded, see the "MemberPress-style options editor" addendum below.
- Still only supports the `"member"` entity type through this admin page - a real constraint if a future Module wants its own admin-manageable fields for a different entity type, though extending it is expected to be a small, mechanical change (parameterize the page, don't redesign the storage).

## Addendum: TYPE_FILE was never actually wired end-to-end

Follow-up ask: "I want at the member fields types to be able to set a field type so that a member can upload a file. At elesyth site where i have used memberpress there are already such fields that i would like to be included at the import." Investigating surfaced that `FieldDefinition::TYPE_FILE` had a validator (`FieldValidator::validateFile()`) and a renderer (`FieldRenderer` emits a file `<input>`) and even a working single-field uploader (`FieldValueService::handleFileUpload()`, backed by `media_handle_upload()`) - but nothing ever called that uploader from either form that actually submits field values. The admin Edit Member Fields form (`MembersModule::handleSaveMemberFields()`) had `enctype="multipart/form-data"` on its `<form>` tag but the handler only ever read `$_POST`, never `$_FILES` - a latent gap since TYPE_FILE was first built, not something broken by this session's other work.

**Fix: `FieldValueService::saveWithUploads()`**, a new method that both callers (the admin form and the Portal's onboarding profile form) now use in place of plain `save()`. It reshapes PHP's native `$_FILES['custom_fields']` array-named-input layout (`['name' => ['key1' => ..., 'key2' => ...], 'type' => [...], ...]`, one sub-array per property) into one `handleFileUpload()` call per field that actually has a file (skipping empty inputs, signaled by `UPLOAD_ERR_NO_FILE`), then passes the remaining plain values through the existing `save()`/validate path unchanged. This reshaping was written once, here, rather than duplicated in `MembersModule` and `PortalModule` separately.

`PortalService::submitForApproval()` and `PortalModule::handleSubmitProfile()` gained the same `$rawFileUploads` pass-through; `templates/public/portal.php`'s editable-profile `<form>` gained `enctype="multipart/form-data"` (it didn't need it before, since nothing rendered a file input from that form until this fix).

The `$rawFileUploads` parameter is typed as `array{name?: mixed, type?: mixed, ...}|null` rather than the more specific `array<string, string>` per property - PHPStan level 8 flagged the specific version as making `reshapeFileUploads()`'s own defensive `is_array()` runtime check "always false," since the docblock was asserting more certainty about raw `$_FILES` shape than a caller can actually guarantee. Loosening the type (not suppressing the check) was the correct fix: the check is real defense against malformed HTTP input, not dead code.

**MemberPress import path required no changes.** `MemberImportService` calls `FieldValueService::save()` (not `saveWithUploads()`), which is correct as-is: an import has no `$_FILES` to reshape, and MemberPress stores its own file-upload custom fields as a plain WP attachment ID in postmeta, which flows through `save()`'s existing validate-then-persist path like any other field value - `FieldValidator::validateFile()` only checks that the value is a positive integer, which an attachment ID already is. A field discovered from MemberPress and set to `TYPE_FILE` on the Member Fields admin page will therefore import correctly with no importer-side code change; this was verified by reading the existing code path, not by adding new handling.

4 new tests added to `FieldValueServiceTest` covering `saveWithUploads()`: mixed text+file save, an empty file input being ignored rather than treated as "upload a file named nothing," `null` (no file inputs at all) being tolerated, and text-field validation still applying when files are also present. 241 tests total, all passing; `composer stan`/`composer cs` both clean.

## Addendum: identity fields, password reset, MemberPress-style options editor, list columns

Follow-up ask, prompted by comparing this plugin's admin against a real MemberPress installation's screenshots: the Members list and Edit Member page showed no name at all, Edit Member had no email/password capability, the Options editor was a raw textarea, and the Members list's columns were fixed. Four changes, all Core/Module (Members + Core\Fields), no ELESYTH-specific logic added anywhere.

**Member gains `firstName`/`lastName` as first-class, nullable columns** (migration 020), the exact same precedent as `email` in migration 008: a CSV-imported or MemberPress-imported member may have no linked WP account at all, so identity data can't live only there. `MemberPressUserSource::fetchRows()` was changed to fetch full `WP_User` objects (was previously `get_users(['fields' => ['ID', 'user_email']])`) so `->first_name`/`->last_name` - magic properties MemberPress' own signup form already populates via usermeta - flow through the generic importer pipeline with no new ELESYTH-specific mapping needed. Every existing hand-built `new Member(...)` reconstruction that had drifted out of sync with the constructor (`MemberService::importRow()`'s update branch, `linkWpUser()`) was audited and fixed while adding the two new properties - `linkWpUser()` in particular would have silently dropped a member's name on every link/relink had this not been caught, a real latent bug introduced by the new properties' existence, not present before this change.

**Password handling is reset-link only, confirmed with the user via AskUserQuestion before writing any code**, given the security stakes: the admin never sees or sets a plaintext password. `MembersModule::sendPasswordResetEmail()` calls `get_password_reset_key()` (core WordPress, `wp-includes/user.php`, always loaded) rather than including `wp-login.php` to get at its `retrieve_password()` - `wp-login.php`'s bottom-of-file switch statement executes unconditionally on include, which would run unrelated login-page-rendering logic against the current request in an admin-context call. The resulting `wp-login.php?action=rp` URL is the identical link WP's own core reset flow sends. `MemberService::createPortalAccountFor()` (new, alongside the existing `registerNewMember()`) lets an admin give an unlinked member a WP account from an email alone - `wp_generate_password()` produces a throwaway password the member never learns, immediately followed by the same reset email.

**The Options editor became a MemberPress-style Name/Value repeater with type-conditional field visibility** (`assets/js/field-definition-editor.js`), replacing the plain textarea flagged as a known gap in this ADR's original Consequences section. No backend change: the repeater still serializes to the same hidden `<textarea name="options">` in the existing `value|Label`-per-line format `CoreServiceProvider::handleSaveFieldDefinition()`'s `parseOptions()` already parses - the redesign is purely how that string gets built in the browser, so the admin-post handler, `FieldDefinitionRepository`, and every test covering them needed zero changes.

**Members-list columns are admin-selectable per field (`show_in_list` on `FieldDefinition`, migration 021), not hardcoded.** The MemberPress screenshot's extra columns (Ιδιότητα, Τηλ., Κιν., etc.) are all ELESYTH's own custom fields - encoding that specific column set into `MembersListTable` would put implementation-specific knowledge into Core, violating ADR-001. Instead, any field can be flagged "Show in Members list" from the same admin UI every field is already managed from; `MembersListTable::get_columns()` appends one column per flagged field and `prepare_items()` batches one `FieldValueService::valuesFor()` call per visible row (at most 20, the existing page size) rather than per cell.

10 new tests (`Member` name withers/`fullName()`/`withIdentity()`, `MemberRepository` name round-trip, `MemberService::linkWpUser`/`updateIdentity`/`createPortalAccountFor`, `MemberImportService` name pass-through and re-import refresh, `FieldDefinitionRepository` `show_in_list` round-trip); 255 tests total, all passing. `handleSaveMemberIdentity`/`handleSendPasswordReset`/`handleCreatePortalAccount` are admin-post glue, per ADR-015 not directly unit tested - verified on real staging instead.

## Addendum: file access control and approval-gated changes

Follow-up ask: TYPE_FILE fields needed to be "correlated with the member account and visible only to admin and maybe to the member himself," and the admin needed to "control if the member can change the file without approval or not" after the initial upload. Two confirmed-with-the-user (AskUserQuestion) design decisions before writing any code: a gated download endpoint rather than just hiding links (WordPress's default upload folder is publicly reachable by URL regardless of what the UI links to), and a "pending swap" model for approval-gated changes (the member's current file keeps working until an admin approves or rejects a replacement, not a hard lock).

**Authorization is Module-level, not Core, even though the file-streaming mechanism itself is Core.** `Core\Fields\Services\FieldFileStreamer::stream( int $attachmentId )` is pure - `get_attached_file()`/`wp_check_filetype()`/`readfile()`, no authorization logic at all - because "does this WP user own this specific member record" is Members-module domain knowledge (`wp_user_id` on `am_members`), and Core must never depend on a Module (ADR-001/002). Two thin, differently-authorized admin-post handlers both call into the same streamer: `MembersModule::handleDownloadMemberFieldFile()` (`manage_options` only) and `PortalModule::handleDownloadOwnFieldFile()` (`PortalService::memberFor( current WP user )` must resolve to the exact member whose field is being requested - the same ownership check the Portal's own access gate already uses). This is the reason there's one Core capability but two Module endpoints instead of one shared endpoint with a role-branch inside it.

**Pending values live on the same `wp_am_field_values` row as the current value** (migration 022: nullable `pending_value`/`pending_submitted_at` columns), not a separate table - there's at most one pending change per field per entity at a time, which this shape enforces for free rather than needing a uniqueness constraint to express it. `FieldValueRepository` gained `setPending()`/`approvePending()`/`rejectPending()`/`pendingFor()`, all hand-written find-then-insert-or-update (same upsert-by-key pattern as `FieldDefinitionRepository`, not raw `INSERT ... ON DUPLICATE KEY UPDATE` - `FakeWpdb`'s test double only ever understood one hardcoded 6-column INSERT shape, and a second, differently-shaped raw SQL statement would have needed its own bespoke parser in the test double for no real benefit over the already-established structured-array upsert pattern).

**`FieldDefinition::requiresApprovalToChange`** (migration 023) is stored generically but only surfaced in the admin UI when Type = File (the same type-conditional JS mechanism the Options repeater already uses) - "replace a pending value" only has an unambiguous meaning for a field with one current artifact like a file; applying it to other types is a deliberately deferred, not attempted, extension. `FieldValueService::saveWithUploads()`/`handleFileUpload()` gained a `bypassApproval` parameter: a replacement (not the field's first-ever value - "after the initial upload" from the request) on a `requiresApprovalToChange` field routes to `setPending()` instead of `set()`, unless the caller bypasses. The admin's own Edit Member Fields save always bypasses (the admin editing a member directly is by definition already the approver); the Portal's onboarding submission (`PortalService::submitForApproval()`) also bypasses, since that whole submission already goes through one holistic admin review via the existing `member_submitted_for_approval` flow - gating individual file fields with a second, separate approval mechanism during that same initial review would just be two approval steps for one event. Only the new, distinct "member updates a file after already being active" path (`PortalService::updateFileFields()`) does not bypass - that is exactly the scenario the gate exists for.

**File fields had to become reachable independent of `canEditProfile()`'s onboarding-only lock.** `PortalService::editableFileFieldsFor( Member $member ): array` returns every visible `TYPE_FILE` field regardless of member status - an active member renewing an expiring document is the scenario driving this whole addendum, and their other, non-file profile fields must stay locked while this doesn't. The Portal template's new "Documents on file" section is shown only when `! $canEditProfile` (during onboarding, file fields are already reachable through the main profile form; showing both at once would just be two upload widgets for the same field).

**Notification wiring follows the same Module-not-Core rule as everything else here.** `PortalModule::handleUpdateFieldFile()` fires `do_action( 'association_manager_field_pending_approval', $member, $fieldKey )` once per field a member's upload routed to pending; `NotificationsModule` listens and dispatches the new `member_field_pending_approval` template (seeded by migration 024, same pattern as migration 017). `Core\Fields` itself never touches the notification system.

13 new tests (`FieldValueRepository` pending round-trip: set/approve/reject/no-op/pendingFor-filtering; `FieldValueService::saveWithUploads()` first-upload-always-direct, replacement-routes-to-pending, bypass-applies-directly, no-approval-required-still-direct; `PortalService::editableFileFieldsFor()` file-type-only filtering, availability for an active member despite `canEditProfile()` being false, current+pending value reporting, and `updateFileFields()` pending routing). 268 tests total, all passing. The two gated download handlers and `FieldFileStreamer` are WP-glue (`readfile()`, raw HTTP headers) - per ADR-015 not directly unit tested, verified on real staging instead (this environment has no live WordPress/browser). `composer stan`/`composer cs` both clean.
